## 2. 当前项目解决的问题

当前系统解决的是一个带身份和权限边界的工单后端基础流程：

1. 用户注册并安全保存密码哈希；
2. 登录获取短期 Access Token；
3. 根据 Token 建立可信用户 ID 和角色；
4. 用户创建并查看自己的工单；
5. AGENT、ADMIN 进行全局查询和顺序状态处理；
6. ADMIN 将工单指派给合法 AGENT；
7. 条件更新识别状态或处理人的并发变化；
8. 状态和指派成功后记录真实操作者；
9. 业务更新与日志写入一起提交或一起回滚。

它目前不是完整客服产品，也不是已经实现 AI 能力的系统。

## 3. 五个最重要的技术设计

### 3.1 JWT 身份边界

客户端不能通过请求体决定 `creator_user_id` 或 `operator_user_id`。Controller 只使用通过 Resource Server 验证的 JWT `sub`，并显式传给 Service。

这使展示字段 `creatorName`、目标处理人 ID 与真实操作者保持清晰区分。

### 3.2 请求级与对象级授权分离

SecurityFilterChain 根据路径和角色判断“能不能调用这一类接口”；TicketService 根据 `creator_user_id` 判断 USER 是否拥有某一张具体工单。

USER 查询他人工单返回 404，既保持统一业务语义，也减少资源存在性泄露。

### 3.3 状态条件更新

状态机负责业务合法性，`WHERE id AND status=旧状态` 负责并发条件。查询后到更新前即使发生变化，UPDATE 也会返回 0 而不是覆盖新值。

### 3.4 指派条件更新

目标用户必须是 AGENT；首次指派要求旧值为 NULL，重新指派要求旧处理人 ID 仍匹配。重复指派与并发冲突使用不同错误码。

### 3.5 业务更新与日志原子提交

状态/指派条件 UPDATE 成功后，在同一个 `@Transactional` 中同步插入操作日志。日志写入失败会回滚工单修改，避免“业务成功但审计缺失”。

事务原子性和条件更新是互补机制：前者约束两个写操作，后者约束并发请求覆盖。

## 4. 典型 3～5 分钟项目讲解结构

### 第一分钟：项目目标和范围

“这是一个基于 Spring Boot 的工单后端。当前完成用户注册登录、JWT 认证、三角色授权、工单创建查询分页、状态流转、管理员指派和操作日志。AI 分类、RAG 等仍是后续规划。”

### 第二分钟：分层与数据模型

说明 Controller、Service、MyBatis-Plus Mapper、MySQL 的调用链，以及 `users`、`tickets`、`ticket_operation_logs` 三张表。强调 Flyway V1～V6 保留可追踪演进。

### 第三分钟：安全边界

说明 BCrypt、HS256 Access Token、JWT claims 校验、角色到 Authority 转换。重点讲请求级授权和 USER 详情对象所有权是两层机制，`creatorName` 不参与授权。

### 第四分钟：并发与事务

用两个条件 UPDATE 说明状态和指派如何防止旧值覆盖；再说明业务 UPDATE 和日志 INSERT 共享事务，日志外键失败时真实数据库测试证明业务回滚。

### 第五分钟：测试和不足

说明 45 个测试类、329 个测试实例覆盖 Validation、单元、MVC、真实 MySQL、HTTP 和 Security；随后主动说明没有压力测试、多节点一致性、Token 撤销、多租户和 AI 功能。

## 5. 当前不足

### 5.1 产品能力

- 没有评论、附件、通知、工单关闭后重开；
- 没有取消指派、主动领取和“分配给我”列表；
- 没有操作日志查询接口；
- TicketResponse 不包含处理人、创建者 ID 和时间字段。

### 5.2 认证与安全

- 只有 HS256 单密钥 Access Token；
- 没有 Refresh Token、撤销、登出、用户停用或密码修改；
- 没有登录限流、验证码和安全渗透测试；
- `anyRequest().permitAll()` 对未来新增端点存在漏配风险；
- `/api/auth/me` 不实时查询账户状态。

### 5.3 数据与并发

- 没有通用 version 字段或真实多线程 HTTP 竞态测试；
- OFFSET 分页没有大数据量性能证据；
- 操作日志是应用层追加式，不是数据库物理不可篡改审计；
- 没有多租户和分布式一致性设计。

### 5.4 工程验证

- 没有压力、容灾、生产部署和备份恢复测试；
- 当前测试依赖本地真实 MySQL；
- Maven Wrapper 在当前 PowerShell 环境未作为验证入口。

## 6. 后续阶段 Roadmap

以下仅为规划：

1. 增加工单操作日志只读查询接口和授权规则；
2. 增加“分配给我”、取消指派或领取的明确业务模型；
3. 增加用户停用、Refresh Token、撤销与密钥轮换策略；
4. 评估 Redis 缓存、限流、登录保护和幂等；
5. 对分页索引、真实并发和大数据量进行专项验证；
6. 在基础业务稳定后增加 AI 分类、优先级建议和回复草稿；
7. 再评估 RAG、Tool Calling、Agent 与人工确认边界。
